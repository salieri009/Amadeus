# Data Pipeline Architecture Patterns (데이터 파이프라인 아키텍처 패턴)

이 문서는 `log_pipeline` 프로젝트에 적용된 업계 표준 아키텍처 패턴들을 학습 목적으로 정리한 내용입니다. 이 설계 구조는 데이터 엔지니어링 및 백엔드 시스템에서 핵심적인 비즈니스 로직을 보호하고, 시스템의 확장성을 극대화하기 위해 널리 사용됩니다.

---

## 1. 포트와 어댑터 패턴 (Ports and Adapters / Hexagonal Architecture)

**개념**: 핵심 비즈니스 로직을 외부 환경(파일 시스템, 데이터베이스, AWS S3 등)으로부터 격리시키는 디자인 패턴입니다.
- **Port (포트)**: 시스템이 외부와 통신하기 위해 정의한 인터페이스 또는 규격입니다. 파이썬에서는 Duck Typing(특정 메서드 시그니처만 공유)을 통해 암묵적인 인터페이스로 다루는 경우가 많습니다.
- **Adapter (어댑터)**: 해당 포트의 규격에 맞춰 실제 외부 시스템과 통신하는 구체화된 구현체입니다.

**프로젝트 적용 사례**:
- **어댑터 구현체**: `LocalFileReader`, `LocalFileWriter`
- **포트 역할**: 입력 시 `read_lines()`, 출력 시 `write_line()`
- **장점**: 파이프라인 엔진(`LogPipeline`)의 내부 로직을 단 한 줄도 수정하지 않고도 `S3FileWriter`, `KafkaReader`, `BigQueryWriter` 등 완전히 다른 형태의 입출력 소스로 즉시 전환(Swapping)이 가능합니다.

---

## 2. 의존성 주입 (Dependency Injection - DI)

**개념**: 객체가 자체적으로 사용할 부품(의존성)을 직접 생성하지 않고, 외부에서 생성 완료된 객체를 전달(주입)받아 사용하는 설계 기법입니다. 컴포넌트 간의 결합도(Coupling)를 낮추는 가장 기본적인 뼈대 역할을 합니다. (Spring, FastAPI 등의 핵심 요소)

**프로젝트 적용 사례**:
- `pipeline.py`의 `LogPipeline` 클래스는 내부에서 파일을 읽기 위해 `LocalFileReader` 인스턴스를 스스로 생성하지 않습니다.
- 대신, 파이프라인의 **가장 밖인 오케스트레이터(`main.py`)**에서 각 어댑터들을 미리 인스턴스화 한 후, `LogPipeline`의 생성자 파라미터(`__init__`)로 전달(주입)해 줍니다.
- **장점**: 파이프라인을 테스트할 때, 실제 로컬 파일을 읽고 쓰는 과정 없이 메모리 기반의 더미(Mock) 리더와 더미 라이터를 인젝션(주입)할 수 있어, I/O 비용 없이 0.001초만에 순수 비즈니스 로직만 완벽히 단위 테스트(Unit Testing) 할 수 있습니다.

---

## 3. 파이프라인 패턴 (Pipeline Pattern / Filter Pattern)

**개념**: 데이터를 일련의 처리 과정(Stage)을 거쳐 차례대로 통과시키는 구조입니다. 일반적으로 시스템이 복잡해지면서 발생하는 "스파게티 코드"를 방지하고 처리 흐름을 일방향으로 만들어 줍니다. 전형적인 데이터 엔지니어링의 ETL(Extract, Transform, Load) 프로세스에 주로 적용됩니다.

**프로젝트 적용 사례**:
- **Extract (추출)**: `reader.read_lines()`를 통해 메모리 과부하 없이 스트리밍 형태로 로그 데이터를 한 줄씩 읽어옵니다.
- **Transform & Validate (변환 및 검증)**: 읽어온 데이터를 Pydantic 라이브러리의 `ServerLog` 모델을 이용해 타입/필수값을 검증하고, Anomaly 탐지(status >= 500, 응답시간 지연 등) 로직을 거칩니다.
- **Load (적재)**: Pydantic 검증의 성공(Valid) 또는 실패(Invalid) 여부에 따라 `processed_writer` 혹은 `quarantine_writer`로 갈래를 나눠(라우팅) 저장합니다.
- **장점**: 데이터 흐름이 단방향으로 명확하며, 미래에 새로운 검증 규칙(예: IP 차단 목록 조회, 외부 API 통신 검증 등)을 파이프라인 중간 단계에 마치 플러그인처럼 쉽게 끼워넣을 수 있습니다.

---

### 🚀 실무 시스템에서의 발전 방향 (Next Steps)

현재의 뼈대 구조를 바탕으로, 실제 대규모 상용 망에서는 다음과 같이 발전하게 됩니다.

1. **분산 스토리지/이벤트 허브 연동**: `S3Adapter`나 `KafkaAdapter`를 도입해 분산 서버 환경의 로그들을 수집.
2. **다단계 필터링(Chain of Responsibility)**: Pydantic 모델 검증 외에도 중복 로그 제거, 민감 정보(PII) 마스킹 등 필터 단계를 여러 개로 쪼개어 연결.
3. **오케스트레이터 자동화**: `main.py`의 실행을 운영체제의 배치가 아닌 **Airflow, Dagster, Prefect** 등 워크플로우 엔진에 등록해 예약 실행(Cron) 및 모니터링 수행.
4. **비동기 성능 향상**: `multiprocessing` 작업자 풀 파생 혹은 Python `asyncio` 기반의 비동기 어댑터를 주입하여 TPS(초당 처리량) 개선.
